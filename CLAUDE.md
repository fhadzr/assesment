## Non-negotiable rules

The overriding engineering principle: **small, working, tested, and honest.**

**Honesty about results**
- Never fabricate metrics or evaluation results.
- All metrics must come from executable scripts — no hand-written numbers in docs.
- Never claim production readiness without evidence.
- Document assumptions and limitations in every case.

**Data**
- All datasets must be synthetic and reproducible (generated by scripts in the repo).

**Security & privacy (applies to every case)**
- No secrets in source code.
- No PII in logs.
- Apply access control **before** LLM context construction — filter what reaches the model, not just what returns to the user.
- Use mock LLM providers in automated tests.
- Never transmit confidential data without authorization.
- Every case must have security tests (results go in `evidence/security_test_results/`).

**SDD discipline**
- Follow approved OpenSpec specifications.
- Implement one logical task at a time.
- Do not silently change requirements — surface the change and update the spec.
- Update tests with implementation.
- Verify all generated outputs.
- Document design decisions (`docs/` per case; experiments in `evidence/experiment_log/`).

**Definition of done** — a task is complete only when ALL hold:
1. Implementation exists.
2. Relevant tests pass.
3. Actual outputs exist.
4. Documentation is updated.
5. Limitations are documented.

## OpenSpec structure

- `openspec/changes/<name>/` — active change proposals (scaffolded by `openspec new change`)
- `openspec/changes/archive/` — completed changes (moved here by `openspec archive`)
- `openspec/specs/<capability>/spec.md` — main (current) specs per capability; only updated by archiving/syncing a change's delta specs, never edited directly as part of normal work
- `openspec/config.yaml` — optional `context` (project constraints) and `rules` (per-artifact rules)
- `.claude/skills/openspec-*` and `.claude/commands/opsx/` — OpenSpec workflow definitions, generated by `openspec update`. Don't hand-edit; regenerate instead.

A change under the spec-driven schema consists of: `proposal.md` (what & why), `specs/<capability>/spec.md` (delta against main specs, not a copy), `design.md` (how), `tasks.md` (implementation steps).

## Workflow

Use the OpenSpec workflow rather than ad-hoc planning. The slash commands and skills are equivalent entry points:

1. `/opsx:propose` — create a change + all planning artifacts. **Planning only: do not edit project code in this step.** Implementation waits for an explicit apply request.
2. `/opsx:apply` — implement tasks from a change's `tasks.md`, marking tasks complete as you go.
3. `/opsx:update` — revise an existing change's artifacts, keeping them coherent.
4. `/opsx:sync` — copy a change's delta specs into main specs without archiving.
5. `/opsx:archive` — finalize a completed change and fold its deltas into main specs.

When these workflows run, follow the instructions they load — they define the authoritative steps (artifact order, status checks, guardrails).

## Common commands

```powershell
openspec list --json                                # changes + resolved root (null root = no openspec/ dir)
openspec list --specs                               # main specs
openspec status --change "<name>" --json            # artifact statuses + dependency edges + paths
openspec instructions <artifact> --change "<name>" --json   # template/rules for one artifact (or "apply")
openspec validate <change-name>                     # validate a change's artifacts
openspec show <name>                                # show a change or spec
openspec archive <change-name>                      # archive + update main specs
openspec doctor                                     # relationship health of the root
openspec update                                     # regenerate .claude/ instruction files (after CLI upgrade)
```

The CLI prints follow-up hints with the right flags — prefer following those over assumptions. Paths it returns (`planningHome`, `changeRoot`, `resolvedOutputPath`) are authoritative; don't hardcode repo-local paths.
